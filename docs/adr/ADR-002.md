# ADR-002 — Fases paralelas com integração serial

- **Status:** accepted
- **Data:** 2026-11-14
- **Fase:** F-metodo-v6
- **emenda ADR-001**

## Contexto

O loop abria uma fase por vez: uma spec no `docs/SETUP.md`, uma branch, um merge no fecho. Dá para executar fases que não se tocam ao mesmo tempo, e o que impede é o método, não o git. O que quebra no paralelo são os mesmos arquivos em toda fase — `CHANGELOG`, `ROADMAP`, `DECISOES`, `DEBITO-TECNICO`, `SETUP-HISTORICO`, `SETUP` — e dois merges chegando juntos. A F-metodo-v5 deixou o canal por id de fase; isso já separa bots. Os scripts do canal (`canal-avisar`, disparador) estavam no ROADMAP como F-metodo-v6 e não cabem nesta fase.

## Decisão

Fase **solitária** — nada em execução e o planejamento abre uma fase só — segue o loop de hoje: spec no `SETUP.md`, sem worktree obrigatório, ledgers editados na branch.

Fase **paralela** — mais de uma fase no mesmo planejamento, ou uma fase nova com outra já no ar, sem arquivo em comum — nasce com `scripts/abrir-fase.sh`: branch `fase/<id>-<slug>`, worktree irmão `<repo>-fases/<id>`, registro `docs/fases-ativas/<id>.md` e fragmento `docs/changes/<id>.md`. O `main` fica limpo. A spec que a execução lê continua sendo o `docs/SETUP.md` daquele worktree.

O registro é um arquivo por fase, na branch dela, não um `docs/fases-ativas.md` único. O planejamento descobre as ativas com `scripts/fases-ativas.sh` (worktree, branch local `fase/*`, `origin/fase/*`). Fase solitária sem registro reivindica o repo inteiro: a próxima espera ou o dono reescopa. Item com dependência não abre; fica na fila até o id estar no `CHANGELOG`.

Quem entra no `main` é `scripts/integrar-fase.sh`, chamado pelo fecho. Uma integração por vez, trava `refs/integracao/lock` no remoto. A branch rebaseia na `main`; conflito trivial de ledger o script junta; o resto para. Em seguida a validação (`scripts/validar.sh`). Só então o merge (`gh pr merge --rebase`, ou fast-forward equivalente no teste). Conflito de lógica, validação que falha ou spec ainda no `SETUP.md`: a trava fica, o merge não acontece, a decisão é do dono. O script pode `push --force-with-lease` só em `fase/*`, depois do rebase. Na mão, o hook continua barrando.

Os scripts do canal passam a ser a **F-metodo-v7**. O contrato v1 não muda.

## Alternativas consideradas

- **Um `docs/fases-ativas.md` só.** Duas fases registrando ao mesmo tempo conflitam no arquivo que existe para evitar conflito.
- **`merge=union` no gitattributes.** Junta linha que uma fase apagou e não entende a troca de uma linha do `ROADMAP`.
- **Fila de merge só no CI.** Projeto sem Actions ficava sem caminho. O script é o caminho; o workflow `validar` só roda a validação, não mergeia.
- **Worktree obrigatório na solitária.** Muda o caso que continua igual ao de hoje.
- **Commit do registro direto na `main`.** Fura "main só recebe merge de PR".
- **Deixar os scripts do canal nesta fase.** O paralelismo já é uma decisão de método; misturar os dois no mesmo id escondia a renumeração.

## Consequências

Dá para planejar e executar fases que não se cruzam enquanto outras correm. O preço é disciplina: a paralela não edita ledger (escreve fragmento), o fecho devolve o `SETUP.md` ao template antes de integrar, e conflito que não é ledger para. A trava esquecida segura a fila até `--abortar` ou até a mesma fase continuar. O teto diário do canal continua por projeto: fases paralelas dividem o mesmo teto, e um POST pode levar ponteiros de fases diferentes. A F-metodo-v7 é que implementa o aviso.
