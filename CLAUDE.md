# CLAUDE.md

`AGENTS.md` é a instrução canônica — **leia primeiro**, tudo lá vale aqui. Este arquivo só mapeia a mecânica do loop pros botões do Claude Code.

## Mecânica no Claude Code

- **Plan mode = a passada de raciocínio.** Nele você audita o código, discute o aberto e **redige a spec no `docs/SETUP.md`**. `ExitPlanMode` (aprovação do plano) = aprovação da spec. Effort alto quando há decisão em aberto (arquitetura, schema/estado, trade-off); modelo mais barato quando a spec já decidiu tudo e o trabalho é mecânico. Não planeje o trivial.
- **Recomendar model/effort, sempre.** Toda spec fechada no plan mode termina com uma linha **`Model/effort de execução: <modelo> · <effort>`** — recomendação explícita pro code mode (por etapa, se variarem). O plan mode também **declara sob qual modelo/effort está rodando** e, se julgar o modelo sub/superdimensionado pra tarefa, **avisa o dono pra trocar** antes de seguir — **proativamente e sem condição**: o aviso não espera o dono perguntar, mesmo que ele possa ter esquecido de trocar. Guia neutro: **modelo forte** = raciocínio pesado / decisão aberta / design; **modelo médio** = execução envolvida padrão; **modelo leve** = mecânico trivial.
- **Autonomia de model/effort em subagentes, em qualquer modo.** Subagentes/Tasks disparados tanto em **plan mode** (pesquisa, exploração, um agente `Plan`, etc.) quanto em **code mode** (revisão de fecho, investigação pontual, etc.) têm model/effort escolhido livremente pelo agente, sem pedir aprovação antes — independente do model/effort da sessão principal do dono, já que cada subagente roda isolado. Exceção: quando a spec já nomeia model/effort explícito pra uma etapa (`delegar a subagente: <modelo> · <effort>`), essa decisão gravada prevalece sobre a escolha livre.
- **`/clear` entre os modos** (não `/compact`): aprovada a spec, o dono limpa o contexto e a execução roda numa sessão nova, lendo só o `SETUP.md`.
- **Inbox de achados, sempre no início do plan mode.** Rode `gh issue list --label achado --state open` antes de auditar o código — o dono usa issues (template `.github/ISSUE_TEMPLATE/achado.md`) como bloco de notas pra problemas e melhorias que vai encontrando. Triagem e fecho de issue seguem `AGENTS.md` §Inbox de achados.
- **Commit por etapa; fecho completo no fim (não perca isto).** Spec com várias etapas: **commite a etapa que terminou antes de iniciar a próxima** — nunca acumule etapas no working tree. No fim da spec, execute o **fecho inteiro sem parar**: commit → PR (`gh`) → merge `--rebase` → apaga a branch (**remota + local**) → `git switch main && git pull`. Ao terminar, `git branch` mostra só `main` atualizado. (Regra canônica e detalhes: `AGENTS.md` §git.)
- **Ambiente é do dono.** Não tente subir/derrubar o ambiente; o dono roda e para o ambiente manualmente. Precisa de restart? Peça. Build, typecheck, lint, testes e leitura de código são livres — não dependem do ambiente rodando. (Detalhe: `AGENTS.md`.)
- **Revisão de fecho = subagente via Task.** Ao fechar a fase, dispare um subagente de **contexto fresco** com só os docs vivos + o diff, pra conferir entregue-vs-spec antes do commit.
- **Passada única de docs:** feche todos os docs vivos afetados (CHANGELOG, ROADMAP, SETUP, DECISOES/DEBITO se aplicável) numa passada antes do commit, pela regra de migração do `AGENTS.md`.
- **Prompts curtos:** o dono aciona fases com instruções curtas (ex.: "planeja a próxima fase", "executa a fase do SETUP"). O contexto vem dos docs vivos, não do prompt.
